Administrator Guide

How to provision ECMS users and manage their access — Profiles, Permission Set Groups, the CBO-specific User Functions picklist, and Queues. This guide is for DOE/ECMS system administrators setting up new users and permissions, not for day-to-day ECMS use by Operations staff, vendors, or FCCN network staff — see the other guides in this collection for that.

Overview — how ECMS access control actually works

Before provisioning anyone, it helps to understand that ECMS splits access control three different ways, and mixing them up is the single most common cause of "why can't this new user see X":

  • Profile — controls which app and basic platform-level permissions a user gets (internal vs. portal, API access, etc.). In ECMS there are only a handful of real Profiles, and — this is the part that surprises new admins — Profile does NOT differentiate between ECMS personas. Every internal DOE persona (Operations Director, Operations Analyst, Enrollment Specialist, Incident Management Team Member…) shares the exact same Profile, ECMS Internal User. Every FCCN external persona shares ECMS Community User.
  • Permission Set Group (PSG) — this is what actually differentiates one persona from another, for both internal DOE users and FCCN external users. A user is typically assigned more than one PSG at once (confirmed live — a single FCCN Network Contact user in this org holds 10+ PSGs simultaneously, one per function they need).
  • ECMS User Functions (CBO vendor users only) — CBO vendor personas work differently from everyone else. Instead of PSGs doing the differentiation, a CBO Contact gets a multi-select picklist field, Contact.ECMS_User_Functions__c, with values like Budget Management, Invoice Management, Site Management, etc. — each one unlocking its own Apex sharing rules for that module. Do not try to provision a CBO vendor user with a PSG the way you would an internal or FCCN user — it's the wrong mechanism for that persona type and won't grant the access you expect.
Rule of thumb: Internal DOE user or FCCN external user → think Profile + PSG. CBO vendor user → think Profile + ECMS User Functions picklist (no PSG involved).

Provisioning an Internal DOE user

1Create a new Internal DOE user

DO First, open Setup: click the gear icon in the top-right of any ECMS screen, then click Setup at the top of the menu that appears.

DO In Setup, go to Administration → Users → Users, then click New User.

RESULT A standard Salesforce New User form opens. Fill in the person's name, a unique Username (must be email-format and globally unique across all Salesforce orgs, not just this one) and Email, set User License to Salesforce, and set Profile to ECMS Internal User.

Note: Leave Role as <None Specified> unless you've been told a specific Role hierarchy reason to set one — ECMS's real persona differentiation happens via PSG assignment (next step), not Role.

2Assign a Permission Set Group

DO Go to Setup > Permission Set Groups, search for the PSG matching the new user's persona (see the reference table below), open it, and click Manage Assignments → Add Assignment.

RESULT The PSG's detail page shows its description, its member Permission Sets, and a Current Assignments list of every user currently holding it. Adding the new user here grants them everything that PSG bundles together.

Note: A user almost always needs more than one PSG. For example, an Operations Director typically also needs ECMS Internal Application User-type base access on top of their role-specific PSG — check the reference table for the full combination, not just one entry.

3Internal persona → Permission Set Group reference

Common miss: PSG assignment alone is not enough for Enrollment Specialists, Operations Analysts, and Incident Management Team members — these three personas also need explicit Queue membership (Step 11) before they can actually see or act on the records routed to them. This is one of the most frequently missed steps when provisioning these personas specifically — a user can hold the correct PSG and still appear to have "no access" simply because no one added them to the matching Queue.

Provisioning an External CBO vendor user

4Enable a CBO vendor Contact for portal access

DO CBO vendor users start life as a Contact record under their Account, and a Site Staff record for them must already exist. If one doesn't exist yet, create it first: open the relevant Site Master record, find its Site Staff related list, and click New.

RESULT A record-type choice appears: ECMS DOE Internal Staff (an internal DOE resource tracked against a Site) or ECMS Vendor Staff (a vendor resource, used for both record-maintenance access and vendor budget staffing). Pick ECMS Vendor Staff for a CBO vendor user.

RESULT The New Site Staff form opens with the Site pre-filled. Search for and select the Vendor Employee (the Contact), then fill in the required Staff Type (and Designation/Teacher Type as applicable), and click Save.

Once the Site Staff record exists, open the Contact, and confirm ECMS Access is checked.

RESULT Once ECMS access is granted and the Contact has been enabled as a portal/partner user (via Provision Contact or the standard "Enable as Partner User" action), action buttons appear on the Contact: Log in to Experience as User, Provision Contact, View Partner User.

Logging in as a vendor. As an internal admin, you'll frequently need to see (or test) exactly what a vendor sees — without needing their password. Click Log in to Experience as User right here on their Contact record. This logs you into their exact portal view, home page, and menus — shown here as Priya Fernandez, Site Director at Willow Brook Children's Learning Center. If you are the vendor yourself (not an admin impersonating one), you don't need any of the above — just go to your organization's ECMS vendor portal URL directly and log in with your own username and password, the same as any website login.

5Provision Contact — grant modules and Sites in one guided flow

DO Click the Provision Contact action button on the Contact. This launches a 3-screen guided flow — this is the mechanism DOE actually uses to give an external user access to modules, not just an inline field edit.

RESULT Screen 1 — Functions: a "Do You Want to Remove All ECMS Functions?" Yes/No choice, followed by a description of what each of the 12 available functions grants (Vendor Management, Site Management, Budget Management, Invoice Management, Classroom Management, Enrollment Management, Attendance Management, Student Screening, Checklist Manager, CBO Incident Management, Reporting and Dashboards, Student Contacts), then checkboxes pre-populated with whatever the Contact already holds — add or remove as needed.

RESULT Screen 2 — Sites: the Sites currently assigned to this Contact appear pre-checked; add or remove Sites the same way.

RESULT Screen 3 — Review & Finish: a plain-text summary of the exact Functions and Sites that will be saved. Clicking Finish writes both in one step — the Functions list writes to the same ECMS User Functions picklist described in Step 6 below, and the Site list writes to this Contact's assigned Sites.

Note: Provision Contact is the guided, recommended path for granting an external user's module access and Site assignment together. Step 6 still documents the underlying ECMS User Functions field directly, since you can also edit it inline on the Contact if you only need to change Functions and not Sites.

6Set ECMS User Functions (CBO only)

DO On the same Contact, scroll to the ECMS Access section and edit ECMS User Functions — a multi-select picklist.

RESULT Each value you add unlocks that module's own Apex sharing rules for this Contact (e.g. adding Budget Management grants read/edit access to Budgets and their related records for this vendor's assigned Sites). A Vendor Admin persona typically holds most or all values; a narrower persona like "Budget Creator" would hold just Budget Management (plus whatever base access it depends on).

Note: This is the single biggest difference between provisioning a CBO user and provisioning anyone else in ECMS — there is no PSG step for CBO vendor personas. Assigning a PSG to a CBO Contact's User won't grant the module-level sharing; the picklist is what does it.

Provisioning an External FCCN user

8Provision an FCCN external user

DO FCCN external users (Network Director, Education Specialist, Monitoring Specialist, Family Worker, Education Director, Affiliation Manager) use the exact same mechanism as Internal DOE users — Profile + Permission Set Group — NOT the User Functions picklist. Set Profile to ECMS Community User, then assign the matching PSG from the table below, the same way as Step 2 above (Setup > Permission Set Groups > find the PSG > Manage Assignments > Add Assignment).

RESULT The user should show all assigned PSGs. Below is a real Network Contact user in this org who holds 14 PSGs at once (one per function — incident reporting, affiliation management, education specialist logs, reporting/dashboards, etc.), all stacked on top of the single ECMS Community User Profile.

Note: Don't confuse "FCCN" with "CBO" when provisioning — they're both external/vendor- side personas, but they use two genuinely different access-control mechanisms (see the Overview above). Using the wrong one is the most common provisioning mistake for external users.

Queues and case/incident routing

Queue membership is mandatory, not optional, for several personas. Having the right PSG does not automatically add someone to the Queue their persona depends on — they are two separate, independent steps. Enrollment Specialists, Operations Analysts, and Incident Management Team members in particular will not be able to act on any routed records until someone also adds them as a Queue member (Step 10) — a very easy step to forget, and one of the most common real provisioning misses seen in this project's own testing.

10View Queues and what they route

DO Go to Setup > Administration > Users > Queues.

RESULT The full list of real Queues in this org, each with a Supported Objects column showing what it routes is displayed. For example: Enrollment Specialists routes Enrollment approval requests, Operations Analysts/Operations Directors route Budget and Budget/Journal approvals, and most Incident-related queues (Intake Team, Level 1 Incidents, Incident Owner Assignment, etc.) route Incident Case.

11Open a Queue and manage its members

DO Click into a Queue's name from the list.

RESULT The Queue detail page shows its supported object(s) and a member list. Use Edit to add or remove members — anyone on this list can see and act on records routed to the queue (e.g. the Enrollment Specialist approval step we rely on throughout the rest of this guide collection routes to whoever is a member of the Enrollment Specialists queue).

Post-Provision Validation Steps

Don't consider a user "done" the moment Profile/PSG (or ECMS User Functions, for CBO) is assigned. Confirm the access actually works end to end — this catches the lag/propagation issues covered in the Troubleshooting section below.

12Validate the new user's access end-to-end

DO Before closing out any provisioning request — internal, CBO, or FCCN — walk through this checklist:

  • User can log in. Internal: have them attempt a normal Salesforce login (or confirm via "Login History" in Setup). CBO/FCCN: use Log in to Experience as User from their Contact, or have the vendor/network user try their own portal login once their account is activated.
  • User sees the ECMS application. Internal: the App Launcher shows ECMS as an available app. CBO/FCCN: the portal home page loads with the expected ECMS branding and navigation — not a blank page or a generic Experience Cloud default.
  • User can access their assigned module and Site. Open the specific tab/module their persona needs (e.g. Enrollments for an Enrollment Specialist, Budgets for a CBO Budget Creator) and confirm it loads without a permissions error.
  • User can see the records they should see. A tab loading is not enough — open an actual real record (a specific Enrollment, Budget, Site, etc.) that this persona should have visibility into, and confirm it opens cleanly rather than showing an "insufficient privileges" or blank-detail error.
  • User receives email notifications, if their persona depends on one. Personas tied to an approval workflow (Enrollment Specialist, OA/OD, Incident team) should receive a real notification/approval email during this check — email deliverability problems look identical to an access problem from the user's side ("I never got anything"), but are a separate issue to diagnose.

RESULT A user who passes all five checks is genuinely ready to use ECMS for their role — not just "has a PSG assigned."

Note: Sharing recalculation after a PSG assignment or Provision Contact grant is not always instant (see Troubleshooting below). If a check fails immediately after provisioning, wait a few minutes and re-check before assuming something is misconfigured.

Deactivating a User

Use this whenever access needs to be fully revoked. Common cases: an employee leaves DOE, vendor staff leaves their organization, or an FCCN worker changes role and needs their old access removed before being re-provisioned under a new persona. Deactivating the User record alone is not sufficient — stale PSG and Queue memberships left behind can silently re-apply if the account is ever reactivated, so all three steps below are required to complete offboarding.

13Deactivate the User record

DO Open the User record (Setup > Users > Users for internal users, or the person's Contact → related User for CBO/FCCN external users), click Edit, uncheck Active, and Save.

RESULT The user can no longer log in, internally or through the portal. Records they previously owned are not deleted or automatically reassigned — review Ownership separately if that matters for your case.

Note: Salesforce does not allow deleting a User record outright — unchecking Active is the correct, and only, way to fully revoke a user's access.

14Remove Permission Set Group assignments

DO For each PSG the user holds, go to Setup > Permission Set Groups, open that PSG, find the user under Manage Assignments, select them, and click Remove. Repeat for every PSG they hold — most real personas hold more than one (see the reference tables above).

RESULT The user no longer inherits that PSG's permissions.

Note: Deactivating the User does not remove their PSG assignments — they stay on record and would silently re-apply if the account is ever reactivated. Always remove them explicitly as a separate offboarding step.

15Remove Queue memberships

DO Go to Setup > Administration > Users > Queues, open each Queue the user belonged to (Enrollment Specialists, Operations Analysts, the Incident-related queues, etc.), click Edit, and remove them from the member list.

RESULT Records routed to that queue going forward are no longer visible to, or actionable by, the deactivated user.

Note: Just like PSGs, Queue membership is not automatically cleared by deactivating the User — it must be removed separately, or the stale membership will reappear if the account is ever reactivated.

Troubleshooting access issues

"The new user can't see any records on a Site/Budget/Enrollment they should have access to."

Sharing recalculation after a PSG assignment, a Contact-level field change, or a Provision Contact grant is not always instant — it can take several minutes for access to take effect. Before concluding something is broken, wait a few minutes and re-check, rather than immediately troubleshooting permissions further.

"I assigned a PSG but the user still can't do X."

Check whether the persona actually needs more than one PSG stacked together — most real personas in this org hold several PSGs at once, not just one. Also confirm you assigned the right kind of access for the persona type: internal/FCCN personas need PSGs; CBO vendor personas need the ECMS User Functions picklist instead (see Overview above) — assigning a PSG to a CBO Contact's User won't substitute for the picklist.

"Which persona should I search Permission Set Groups for?"

Never guess a PSG name from what seems logical — search live and confirm the description field, which usually states plainly what the PSG is for (e.g. ECMS Admin Internal's own description: "provides the ability to provision internal & external users, load data files and setup fiscal years"). The reference tables in this guide reflect what's live in UAT today, but PSGs can be added or renamed over time.
